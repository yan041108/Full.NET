# Full.NET 未来架构演进参考

## 当前基线

Full.NET 当前基线是强化型模块化单体：API、Worker、Migrator 按运行角色分离，模块拥有自己的数据与强不变量，跨模块通过最小 Contract Port、版本化事件、本地投影和 Outbox 协作；正式数据库支持仍是 SQL Server/MySQL 双提供程序。

下述微服务、分片、多数据库和云模式只用于未来架构演进评审，不得作为当前默认方案。没有批准的 Spec/ADR、可复现瓶颈和迁移回退证据时，禁止把候选模式写入生产实现。事务 Outbox 的 CDC/Kafka 演进已由 [`ADR-0006`](../../../../docs/architecture/adr/ADR-0006-transactional-outbox-cdc-kafka-event-delivery.md) 单独批准提前实施，但它不构成微服务、分片或多数据库授权，生产切流仍受该 ADR 的单一发布所有权与双库门禁约束。

## 微软云架构知识的采用方式

选择性参考微软官方 [`cloud-solution-architect`](https://github.com/microsoft/skills/tree/main/.github/skills/cloud-solution-architect) 与 [Azure Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/)。可用于候选分析的内容包括：

- N-tier、Web-Queue-Worker、微服务、事件驱动等架构风格；
- Bulkhead、Circuit Breaker、Retry、Compensating Transaction、Saga、CQRS、Materialized View、Cache-Aside、Sharding 等模式；
- Reliability、Security、Cost Optimization、Operational Excellence、Performance Efficiency 五个评审维度；
- Busy Database、Chatty I/O、Retry Storm、Synchronous I/O、Noisy Neighbor 等性能反模式。

这些模式是问题求解工具，不是目标架构清单。不得为了“云原生”数量、瞬时 QPS 或技术流行度引入网络边界、异构存储或分片。

## 证据门禁

### 微服务

只有同时具备以下证据才进入拆分实验：

1. 单体内模块边界已经稳定，且模块间不存在跨表、跨模块本地事务或隐藏共享状态。
2. 独立部署、独立扩缩、故障隔离、合规隔离或团队自治中至少一项形成持续且可量化的收益。
3. 已在模块化单体内完成进程内 Contract、版本事件、Outbox、幂等、补偿、Trace 和 SLO 验证。
4. 网络延迟、部分失败、契约版本、发布编排、回滚、值班和成本已有负责人及预算。
5. 通过一个可回退的候选模块实验，而不是全面微服务化。

不满足任一项时，继续在模块化单体内改善边界、纵向切片和运行角色扩缩。

### 数据库分片

只有同时具备以下证据才评估 Sharding：

1. 在生产等价环境证明单实例或现有高可用拓扑达到容量、I/O、存储、锁或维护窗口上限，且索引、SQL、缓存、批处理和纵向/横向扩容已不能经济解决。
2. 存在稳定、高基数、分布均匀的分片键，并能明确处理热点租户。
3. 已定义路由、跨分片查询、分页、唯一性、事务、再平衡、备份恢复、扩容和故障隔离语义。
4. 双库策略已明确：SQL Server 与 MySQL 是替代 Provider 还是同时运行的分片实现，禁止模糊为“双写即高可用”。
5. 具备影子流量、校验、回滚和数据修复工具。

在以上门禁关闭前，默认使用单数据库内的模块所有权、索引、分区表、读模型、缓存和批处理优化。

### 多数据库与异构存储

只有真实工作负载无法由现有关系模型经济满足时才评估多数据库或 Polyglot Persistence：

- 明确关系事务、文档、搜索、时序、对象、缓存或流式存储的不可替代需求；
- 为每类数据指定唯一权威源、数据所有者、保留策略、加密、备份、恢复和删除语义；
- 明确复制延迟、冲突解决、重建、对账和灾难恢复；
- 评估驱动、许可证、供应商锁定、运维技能、监控和总成本；
- 禁止模块直接读取其他模块数据库，禁止用跨库 JOIN 恢复单体耦合。

SQL Server/MySQL 双提供程序是同一产品能力的可替代实现，不自动等于运行时多数据库架构。

## 分阶段演进顺序

| 阶段 | 默认动作 | 进入下一阶段的证据 |
| --- | --- | --- |
| E0 模块化单体 | 收紧模块所有权、纵向切片、Dapper 双库、Outbox、权限和可观测性 | 当前边界可验证且基准稳定 |
| E1 运行角色扩缩 | 独立扩缩 API/Worker，使用缓存、队列、批处理和数据库原生高可用 | 仍有可复现的独立故障域或扩缩瓶颈 |
| E1.5 可靠事件总线 | 追加式 Outbox、SQL Server CDC/MySQL Binlog、Kafka、消费 Inbox、影子验证和单流切换 | 双库故障矩阵、生产等价延迟/恢复证据与单一 Relay 所有权均通过 |
| E2 边界预拆分 | 稳定 Contract、事件、本地投影、幂等、补偿和 SLO | 候选模块可在进程外运行且行为一致 |
| E3 选择性服务拆分 | 仅迁出一个高收益模块，保留回退路径 | 生产等价验证证明收益大于复杂度 |
| E4 分片或多数据库 | 对单一受限数据域实施路由、对账、恢复和容量治理 | 长期容量与成本证据支持继续扩展 |

禁止跳级；每一阶段都必须保留回滚或停止条件。

## 评审输出契约

架构演进评审必须按以下顺序输出：

1. 当前状态与量化问题：P95/P99、吞吐、容量、RTO/RPO、故障域、成本和团队边界。
2. 保持当前架构的优化方案。
3. 微服务、分片或多数据库候选的收益、代价与失败模式。
4. 对可靠性、安全、成本、运维和性能的权衡矩阵。
5. 最小实验、成功阈值、失败阈值、停止条件和回滚方案。
6. 需要批准的 Spec/ADR、迁移计划和验证记录。

缺少量化证据时，结论必须标记为“探索候选”，不能标记为已批准设计或开发任务。

## 常见误用

- 把运行角色分离或多副本部署误称为微服务。
- 因单条慢 SQL 未优化就引入分片。
- 把 SQL Server/MySQL 双 Provider 误称为生产双写或多主架构。
- 使用 Saga、CQRS 或 Event Sourcing 只为模式完整，而没有业务不变量和恢复需求。
- 用缓存、消息或多数据库隐藏跨模块所有权不清。
- 没有 SLO、可观测性、备份恢复和回滚就宣称架构升级完成。
