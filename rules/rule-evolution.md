# Full.NET 规则自我迭代机制

## 1. 授权与目标

项目所有者已于 2026-07-17 授权：后续开发按推荐方案自动确认，并在开发中自动分析遗漏、总结经验、形成新的项目规则。该授权仅适用于本仓库内规则文件的维护，不扩大代码、发布、外部系统或破坏性操作的授权范围。

每项开发、修复、重构、审查或合并任务结束前，开发代理必须执行一次规则复盘。目标是让重复错误逐渐变成可执行防护，而不是让规则数量无限增长。

规则复盘处理“必须遵守什么”。完成本文件流程后，必须继续执行 [`skill-evolution.md`](skill-evolution.md)，判断重复且稳定的复杂工作流是否应形成项目 Skill；禁止用 Skill 替代强制安全、数据或许可规则。

## 2. 复盘输入

必须检查以下证据：

1. 用户在本次任务中作出的纠正、补充或偏好确认；
2. 构建、测试、静态检查、基准和运行验证中的失败；
3. 代码审查发现的安全、数据、并发、兼容性或维护性问题；
4. 为完成任务重复执行的人工检查，以及本可由测试或工具阻止的遗漏；
5. 新的长期架构决策、技术选型、发布边界或交付约束；
6. 文档与实现、计划与现状、单机与生产拓扑之间的偏差；
7. Git 合并、分支清理、编码、换行和跨平台操作中的问题。

没有新证据时，必须明确得出“本次无新增规则”，禁止为了表现自我迭代而制造规则。

## 3. 发现分类

### A. 单次任务缺陷

条件：原因仅属于本次实现疏忽，已有规则已经明确覆盖，或问题无法合理复现。

处理：修复代码、测试或文档，并指出违反的既有规则；禁止再添加近义规则。

### B. 候选经验

条件：可能复现，但证据不足以成为长期强制约束。

处理：在本文件“候选经验登记区”记录事实、预防方式和出现次数。后续任务再次命中时更新同一条目，禁止创建重复候选。

### C. 强制规则

条件：满足第 4 节至少一个升级门槛。

处理：必须在同一任务中更新最具体的规则文件、补充可执行验证，并在最终交付中列出新增或变更的规则。

## 4. 升级门槛

满足以下任一条件时，候选经验必须升级为强制规则：

1. **重复性**：同类遗漏在不同任务中出现至少两次；
2. **高风险**：一次出现即可导致安全漏洞、租户越权、数据损坏、许可证违规、生产不可恢复或不可逆外部影响；
3. **明确决策**：项目所有者明确确认其为长期技术选型、语言规范、架构边界或交付要求；
4. **规则歧义**：已有规则因表达不清、冲突或缺少验证方式而导致错误执行。

单纯个人风格、未经验证的偏好、一次性的环境故障、特定机器路径和第三方短暂异常不得升级为永久规则。

## 5. 自动演进流程

每项任务完成前必须按顺序执行：

1. **提取事实**：只记录实际发生的纠正、失败、审查结论或架构决定，不推测不存在的问题。
2. **查重**：使用 `rg` 搜索 `AGENTS.md` 与 `rules/`，确认是否已有同义规则或候选。
3. **分类**：按单次缺陷、候选经验或强制规则处理；已有规则覆盖时优先修正执行，不重复写规则。
4. **选择位置**：入口级约束写入 `AGENTS.md`；注释要求写入 `code-comments.md`；开发遗漏写入 `development-quality.md`；治理机制写入本文件。
5. **编写规则**：说明来源、适用范围、强制行为、风险和验证方式，使用“必须/禁止/应/可”的明确措辞。
6. **优先自动化**：可由单元测试、架构测试、分析器、CI、迁移测试或脚本稳定检查的规则，应同时规划或实现自动化，不能永远只靠文字提醒。
7. **检查冲突**：确认新规则不覆盖更高优先级指令，不放宽安全与许可边界，不与现有规则重复或冲突。
8. **验证并披露**：运行链接、占位符、编码和 `git diff --check` 检查；在交付说明中列出规则变化和触发证据。

## 6. 强制规则条目模板

需要新增独立规则条目时使用以下结构；对现有章节的直接澄清可在提交说明中记录来源，无需机械增加编号。

```markdown
### R-YYYYMMDD-简短英文标识：中文标题

- 状态：强制
- 来源：用户决策、重复遗漏、审查编号或事故记录
- 适用范围：具体目录、组件或任务类型
- 风险：不遵守会造成的可验证后果
- 规则：必须或禁止执行的具体行为
- 验证：命令、测试、审查问题或自动化检查
- 例外：允许偏离的条件和所需授权；没有例外时写“无”
```

规则标识一旦发布不得复用。规则重命名时保留原标识或在退役条目中指向替代规则。

## 8. 防止规则失控

1. 每项任务只执行一次结束复盘。规则变更产生的文字调整不得递归触发新的复盘循环。
2. 优先增强一条现有规则，禁止用多个近义条目重复表达同一要求。
3. 规则必须约束可观察行为，不得规定无法验证的心理过程、空泛品质或固定工具品牌偏好。
4. 禁止为了让当前实现“合规”而降低既有安全、测试、数据或许可要求。
5. 自动更新规则后必须报告文件与摘要；用户可审查、修改或撤销，开发代理不得隐藏自修改行为。
6. 规则文件过长或主题混杂时应先设计拆分方案，禁止在一次无关任务中大规模重写全部规则。

## 9. 冲突、替换与退役

1. 发现冲突时先服从更高优先级和最近的明确决策，再在同一任务中消除项目规则冲突。
2. 技术选型改变时，新规则必须明确替换对象、迁移条件和生效范围。
3. 规则失效时必须标记“已退役”、说明原因和替代项；确认仓库不再引用后可在后续聚焦提交中删除。
4. 每个里程碑至少审查一次：重复规则、失效链接、过期版本、无法执行的检查以及可升级为自动化的人工步骤。

## 10. 任务交付格式

最终交付必须包含一项简短的规则复盘结果：

- **无变化**：说明本次没有达到新增或修改规则的门槛；或
- **已演进**：列出触发证据、修改的规则文件和新增自动化；或
- **候选经验**：列出登记标识、出现次数和仍缺少的证据。

不得仅写“已自我迭代”而不提供可审查的文件差异或结论。

完成上述规则结论后，还必须附上 Skills 复盘结论；格式见 [`skill-evolution.md`](skill-evolution.md)。
