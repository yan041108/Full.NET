# Full.NET 性能工程规则

## R-20260727-performance-evidence-boundary：性能优化必须以可重复证据和语义不退化为门禁

- 状态：强制
- 来源：项目所有者于 2026-07-27 要求执行性能审查建议，并于 2026-08-01 封板万级在途、多实例、缓存与 Audit/日志边界；请求链数据库往返、同步 Audit、分页、Worker 空等和管理端包体均需要统一证据门禁
- 适用范围：API、Worker、Migrator、Dapper SQL、SQL Server/MySQL、FusionCache、Outbox、Jobs、Audit、Vue/Layui、基准与负载测试
- 风险：凭静态代码或单次墙钟时间宣称优化，会把安全、租户、可靠性、双库兼容或尾延迟退化隐藏在平均值之后
- 例外：无。紧急生产缓解仍须记录前后指标、范围、回滚条件和未验证项

## 1. 性能契约

1. 性能变更必须在实现前定义场景、数据规模、并发、预热、时长、运行环境、Provider、基线提交和验收指标。
2. 与请求或后台消费相关的验证至少覆盖吞吐、错误率、P50、P95、P99 和资源饱和指标中受影响项；禁止只比较平均值。
3. BenchmarkDotNet 必须使用 Release、记录运行环境并使用真实领域 DTO 或热路径；微基准不能替代数据库、网络或端到端压测。
4. 静态审查只能登记风险和假设。没有相同环境、相同数据、相同场景的前后证据时，禁止宣称吞吐或延迟已提升。

## 2. 请求链与数据库

1. 新增或修改请求热路径时必须列出认证、租户、授权、SQL、缓存、外部调用、Audit 和序列化的同步等待次数。
2. Dapper 性能指标必须使用稳定 Statement 名称、Provider、操作和结果等低基数标签；禁止记录原始 SQL、参数、URL、用户、租户或异常消息。
3. 同一响应需要总数和列表时应优先评估 QueryMultiple；高容量历史表应优先评估稳定游标分页。继续使用深 OFFSET 或 contains 扫描时必须提供数据规模、执行计划和上界。
4. SQL、索引、迁移、锁或分页行为变化必须成对提供 SQL Server/MySQL 实现、执行计划与真实集成验证。

## 3. 安全、Audit 与缓存

1. Session、API Key、安全戳、权限和租户状态缓存必须保持 `rules/development-quality.md` 第 8 节的安全关键缓存语义；性能收益不能放宽撤销时效或 fail-closed。
2. 缓存失效禁止使用 Outbox。事务提交后当前实例直接清理 L1/L2，Redis Backplane 快速通知其他实例，以 TTL、版本与权威源回退兜底；分布式锁只用于有击穿证据的昂贵热点回填。
3. Audit 必须先分类：B0 Domain Audit 与业务状态在同一数据库事务直接写入并 fail-closed；B1 重要 HTTP Operation/Exception Audit 使用有界跨请求微批直接写入审计库，请求等待写入尝试并默认 fail-open + 告警；B2 普通 HTTP Operation Log/Access/诊断进入有界日志管道并可采样。Audit 不使用 Outbox，禁止逐条连接写库、无界队列和无人观察任务。
4. 对 Audit/日志做异步或批量优化前必须明确分类、容量、背压、最大批量/等待、关闭排空、崩溃丢失预算、失败恢复与自监控；不能满足对应可靠性要求时停止变更。

## 4. Worker 与并发

1. 轮询 Worker 取得满批次时必须立即继续领取，未满批次才等待；偏离时必须以外部限流或数据库保护证据说明原因。
2. BatchSize、Poll、Lease 和并行度必须有配置边界，并验证空队列、持续积压、慢 Handler、多实例竞争、崩溃恢复和取消。
3. 禁止批次内逐条重复读取相同目录或定义形成 N+1；合并读取仍必须保持模块所有权、参数化 SQL 和租户边界。
4. 并行处理必须定义顺序键、Handler 作用域、连接池预算和最大并发；禁止只把串行循环改为无界 `Task.WhenAll`。
5. 数据库队列领取必须与续租、成功、失败等终态更新保持一致锁顺序，并使用 Provider 原生非阻塞竞争语义；SQL Server 应评估 `UPDLOCK`/`READPAST`，MySQL 8 应在短事务内使用 `FOR UPDATE SKIP LOCKED` 锁定候选后再按主键更新。验证必须覆盖领取与终态更新并发，且不得用测试重试掩盖死锁。

## 5. 客户端包体

1. Vue/Layui 新增后台页面时必须评估路由动态导入，Vue 的 ECharts 继续按需注册。
2. 生产构建必须记录 minified 与 gzip；发布环境具备 Brotli 时同步记录 Brotli。包体门禁采用基线相对退化，不能只提高 Vite 告警阈值隐藏增长。
3. 拆包不得改变服务端导航白名单、权限、租户、错误处理或双端关键流程；必须运行受影响客户端测试和生产构建。
4. Vue/Layui 的首屏静态 JavaScript 依赖图必须通过 `pnpm test:bundle-budgets`；修改基线必须附带同环境构建证据、变化原因和新的停止条件，禁止用更新基线掩盖无意退化。
5. ECharts、UI 运行库等大体积延迟 chunk 必须建立独立相对预算；禁止只把依赖移出首屏静态图来规避总体积回涨门禁。延迟时机必须以浏览器资源瀑布和关键交互验证，不能仅凭构建拆包结果宣称首屏体验提升。

## 6. 验证与披露

1. 性能 Verification 保存到 `docs/verification/`，包含日期、代码基线、环境、命令、原始结果、结论和未验证项。
2. 共享宿主、认证、Dapper、Outbox、缓存或数据库行为变化按 `development-quality.md` 第 11.1 节运行相应 Integration；环境缺失不得写成通过。
3. 完成前必须运行受影响测试、Release 构建、`git diff --check` 和工作区检查。
4. 重复执行流程使用项目 Skill `$fullnet-performance-hardening`；规则约束不能只存在于 Skill。
5. 开发阶段不要求达到 1 万同时在途，只验证高并发设计、正确性、资源边界与轻量回归；没有专用生产等价容量证据时必须标记 `Capacity-not-verified`，不得承诺固定 QPS。

## 7. 本地反馈与完整性能矩阵

1. 本地代码修改只运行受影响的 Unit、1 个 SQL Server smoke 和 1 个 MySQL smoke；三个验证都必须直接覆盖本次变化，不得因共享路径或历史测试范围自动扩大为全量。
2. 性能候选 A/B 每次只运行发生变化的场景，通常保留 2–4 个可比较样本；扩大样本数前必须说明新增样本要消除的具体不确定性。
3. 完整 Outbox 210 样本和 Audit 600 秒矩阵只能由夜间或手动 CI 性能工作流运行，禁止在普通本地开发任务中执行。
4. 没有代码、SQL、配置或脚本行为变化时，禁止继续刷新性能样本；应复用并披露当前基线或检查点，把任务推进到下一项开发工作。
5. Outbox 和 Jobs 的默认并发必须保持为 `1`。只有 SQL Server 与 MySQL 都取得可重复收益，并同时验证正确性、锁等待、连接池预算、租约和重复处理风险后，才允许调整默认值。
6. 2K/5K/10K、Soak、N+1 与故障注入只在专用容量环境执行；本地任务不得因缺少目标硬件而阻塞功能交付，也不得把缩小矩阵结果包装成正式容量认证。
