# Full.NET 代码注释规则

## 1. 目标与适用范围

注释用于保存代码本身无法完整表达的设计意图、边界、不变量、风险和取舍。规则适用于新增或修改的 C#、SQL、配置、脚本和测试代码。

本规则不要求一次性补齐所有存量代码，但修改现有文件时，必须同步补齐或修正本次变更涉及的注释。不得借“补注释”进行未经授权的大范围重写。

## 2. 语言与表达

1. 代码标识符、命名空间、文件名和公开协议字段必须使用清晰英文。
2. 所有手写源代码注释必须使用清晰中文，包括 `//`、`/* */`、XML 文档注释、SQL 注释和脚本注释。
3. `Dapper`、`Outbox`、`ProblemDetails`、类型名、方法名和标准协议名等专业术语可保留英文，不要求生硬翻译。
4. 注释必须使用完整、明确的陈述句，避免“这里处理一下”“特殊逻辑”“暂时这样”等不可验证措辞。
5. 复制或生成的第三方代码不得为满足语言规则而直接改写；必须标明来源，并遵守其生成或许可约束。

## 3. 必须注释的场景

### 3.1 公共契约与扩展点

新增或修改的 `public`、`protected` API 以及供模块实现的接口必须提供中文 XML 文档注释，至少说明用途。出现下列情况时还必须补充对应标签：

- 参数含义不能从名称准确得出时，使用 `<param>`；
- 返回值包含空值、失败状态、分页或所有权语义时，使用 `<returns>`；
- 调用方需要处理特定异常时，使用 `<exception>`；
- 存在线程安全、生命周期、顺序、幂等或兼容约束时，使用 `<remarks>`。

显然的内部属性、简单数据载体和只在测试内使用的局部辅助方法不要求机械添加注释；如果它们承担业务或协议语义，仍必须说明。

### 3.2 非显然行为与不变量

下列逻辑必须在最接近实现的位置说明“为什么”和“必须保持什么”：

- 租户解析、租户过滤和跨租户管理边界；
- 认证、授权、权限继承和敏感数据脱敏；
- 事务边界、并发控制、锁、租约、幂等、重试和补偿；
- Outbox 的领取、续租、发布、失败与毒消息策略；
- 缓存键组成、失效时机、多实例一致性和防击穿策略；
- MessagePack、JSON、gRPC 或 Admin.NET 兼容层的线格式约束；
- 反射、源生成、Native AOT、裁剪或性能优化所依赖的非显然条件；
- 为兼容第三方组件、数据库差异或运行时缺陷采用的变通方案；
- 数字、超时、批大小、阈值和排序规则不是显然业务常量时。

### 3.3 手写 SQL 与迁移

1. 迁移脚本开头必须说明目的、影响对象、提供程序差异和不可逆风险；纯建库首版脚本可简化，但仍须说明用途。
2. SQL Server 与 MySQL 使用不同语法实现同一语义时，必须分别解释差异原因，不能只说明“数据库不同”。
3. 复杂查询必须说明租户边界、索引假设、锁行为或分页稳定性；禁止逐句翻译 SQL。
4. 所有参数仍必须参数化；注释不能替代防注入、事务或范围守卫。
5. **数据库元数据注释**：新建或修改表/列时，必须在迁移中写入数据库级中文说明（MySQL `COMMENT`、SQL Server `MS_Description`），并与 `contracts/database/object-comments.json` 保持一致；细则见 [`naming-conventions.md`](naming-conventions.md) 第 6.1 节。

### 3.4 配置、脚本与运维约束

配置项的注释应说明单位、默认值、安全范围、重启要求和失败影响。示例中禁止放入真实密钥、令牌或连接密码。脚本中有破坏性、递归或环境依赖操作时，必须说明前置条件和目标范围。

### 3.5 测试代码

测试名称应优先表达场景和期望，注释只补充无法从名称得出的背景，例如历史缺陷、并发时序、数据库限制或为何使用特殊替身。禁止用注释掩盖含糊的测试名称。

## 4. XML 文档注释格式

有效示例：

```csharp
/// <summary>
/// 在当前数据库事务中写入集成事件，供 Outbox 后台任务可靠发布。
/// </summary>
/// <remarks>
/// 调用方必须先开始命令事务；该方法只保证与业务写入原子提交，不保证消息只发布一次。
/// </remarks>
/// <param name="envelope">包含租户、事件类型和序列化载荷的事件信封。</param>
/// <param name="cancellationToken">用于取消数据库操作的令牌。</param>
Task WriteAsync(OutboxEnvelope envelope, CancellationToken cancellationToken);
```

无效示例：

```csharp
/// <summary>
/// 写入异步。
/// </summary>
Task WriteAsync(OutboxEnvelope envelope, CancellationToken cancellationToken);
```

无效示例只重复了方法名，没有说明事务前置条件和交付语义。

## 5. 行内注释格式

有效示例：

```csharp
// 先写业务数据再写 Outbox，但二者共享同一事务；交换顺序会破坏失败回滚测试的前提。
await repository.SaveAsync(tenant, cancellationToken);
await outboxWriter.WriteAsync(envelope, cancellationToken);
```

无效示例：

```csharp
// 保存租户。
await repository.SaveAsync(tenant, cancellationToken);
```

行内注释应放在相关代码之前。只有极短的单位或位标志说明可使用行尾注释，禁止形成难以对齐的注释列。

## 6. TODO、临时方案与注释掉代码

1. 禁止提交长期保留的注释掉代码；Git 已负责保存历史。
2. 禁止没有跟踪信息和退出条件的 `TODO`、`FIXME`、`HACK`。
3. 确需保留时必须使用以下格式，并确保跟踪标识真实存在：

```csharp
// TODO(FULLNET-123): 等待 MySQL 驱动支持异步批量复制；驱动升级并通过双库集成测试后删除。
```

4. 临时兼容逻辑必须说明触发条件、风险、替换条件和对应测试；到达删除条件时必须在同一变更中删除注释与代码。

## 7. 注释维护要求

1. 修改行为时必须同步检查附近注释、XML 文档、示例和测试说明。
2. 注释与代码冲突时，必须以已验证行为为依据修正两者；禁止只改注释来掩盖缺陷。
3. 重命名类型、参数或配置项时必须更新所有相关注释和文档链接。
4. 代码审查必须把错误注释视为缺陷，而不是非阻塞的文字问题。
5. 生成公开 NuGet XML 文档时，必须确认中文字符以 UTF-8 正确输出并能被 IDE 展示。

## 8. 完成检查

提交新增或修改的代码前必须逐项确认：

- 公共契约、扩展点和配置项的用途是否已说明；
- 事务、租户、安全、并发、缓存和协议不变量是否已说明；
- 注释是否解释原因而非复述语法；
- 所有手写源代码注释是否为清晰中文；
- 是否存在过期注释、注释掉代码或无跟踪信息的 TODO；
- 行为、测试、注释和文档是否一致。
