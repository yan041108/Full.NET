# Integration 测试反馈提速实施计划

日期：2026-07-26
状态：已完成

## 目标

在不降低 SQL Server/MySQL 双提供程序、租户隔离和共享基础设施回归保障的前提下，将日常开发从“每次都等待 172 项全量 Integration”调整为分层验证，并缩短 CI 全量门禁的墙钟时间。

## 已确认瓶颈

1. Integration 程序集初始化时无条件启动 SQL Server、MySQL、Redis，导致单提供程序聚焦测试仍承担全部容器冷启动成本。
2. API 测试在大量测试方法中重复创建数据库、执行迁移、启动宿主、创建租户并引导管理员；这是全量运行的主要累计成本。
3. 当前规则把所有过滤运行都视为中间验证，完成前仍要求 172 项全量测试，无法按变更风险分层。
4. CI 的 172 项全量测试集中在单一作业，SQL Server、MySQL、迁移和其他基础设施测试不能并行消化。
5. 已生成 TRX，但没有自动汇总最慢测试、类别和提供程序，优化缺少稳定基线。

## 实施步骤

### 1. 建立反馈性能契约

- 新增静态治理测试，约束按需启动容器、标准命令、分层门禁、CI 分片和 TRX 分析入口。
- 扩展项目 Skill 契约测试，确保后续会话不会恢复“所有局部改动都跑全量”的旧规则。
- 先观察契约失败，再实现对应能力。

### 2. 按需启动测试依赖

- Assembly 初始化不再同时启动 SQL Server、MySQL、Redis。
- 首次请求某个依赖时通过异步锁启动对应容器，后续测试复用容器实例。
- 保持每个测试数据库独立，不改变现有数据隔离语义。

### 3. 标准化分层测试命令

- 提供 smoke、SQL Server API、MySQL API、迁移、其他基础设施和 full 命令。
- 聚焦命令必须带最低发现数量门槛，防止过滤器拼错后出现“零测试成功”。
- full 命令继续验证 172 项基线，并输出 TRX。

### 4. 自动分析耗时

- 从 TRX 输出总耗时、成功/失败数量、最慢测试以及按测试套件和数据库提供程序聚合的耗时。
- CI 上传 TRX 前自动生成可读摘要，为下一轮优化提供证据。

### 5. 分层门禁与 CI 分片

- 普通模块改动只运行受影响测试；SQL、事务、租户过滤和迁移改动必须覆盖双提供程序。
- 共享宿主、认证授权、租户、Outbox、缓存、迁移框架或测试基础设施变更，以及 main/release 门禁，继续运行全量 Integration。
- main 的全量门禁拆分为 API SQL Server、API MySQL、迁移、其他基础设施四个并行分片，并增加一个汇总门禁。

### 6. Factory/数据库基线复用评估

- 不在本轮直接共享可变数据库。现有测试会修改默认租户、角色、权限和后台任务状态，跨测试共享会造成顺序依赖和并发污染。
- 先通过 TRX 确认迁移、宿主启动、密码哈希和引导流程各自占比。
- 后续只有在建立可靠重置协议或数据库模板克隆机制、并通过并发与双库验证后，才允许复用迁移后基线。

## 验收条件

1. 单 SQL Server 或单 MySQL 聚焦测试不会启动未使用的数据库容器或 Redis。
2. 分层命令均具备明确过滤器与最低测试数量门槛。
3. TRX 分析器有自动化测试并能处理 Integration 结果。
4. CI 分片覆盖全部 Integration 测试且不存在重复或遗漏。
5. 规则、项目 Skill、开发文档和 CI 文档同步更新。
6. 相关治理测试、Skill 测试、构建、测试、`git diff --check` 全部通过。

## 完成结果

- 四分片发现与运行：**34/34 + 34/34 + 62/62 + 42/42 = 172/172**。
- 最慢分片为 MySQL API **15分31秒**；main CI 并行临界路径由原单作业 **31分13秒** 降为约 **16 分钟级**，真实 CI 时间以后续 Hosted Runner 结果为准。
- 双库 smoke **8/8**，墙钟 **2分13秒**，运行期间未启动 Redis。
- Factory/迁移后数据库模板复用因可变状态隔离证据不足未启用，后续条件记录于验证报告。
- 验证事实见 [`docs/verification/integration-test-feedback-2026-07-26.md`](../../verification/integration-test-feedback-2026-07-26.md)。
