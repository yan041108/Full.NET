# MySQL UUID Binary16 迁移维护窗口 Runbook

## 1. 目的与边界

本 Runbook 约束 Full.NET 在 MySQL 中将 001–007 的 UUID `char(36)` 存储迁移为 RFC 9562 网络字节序 `BINARY(16)` 的维护窗口。机器清单以 [`UuidStorageContractV1`](../../contracts/database/uuid-storage-v1.json) 为准，008 只执行 Expand，009 才执行不可兼容的 Contract 切换。

SQL Server 保持 `uniqueidentifier`，但必须与同编号迁移一起验证显式主键和聚集索引策略。任何步骤不得使用 `Guid.ToByteArray()`、time-swap、`UUID_TO_BIN(value, 1)` 或 `FOREIGN_KEY_CHECKS=0` 绕过数据问题。

本 Runbook 不是当前可执行发布授权。008、009、连接策略和恢复测试尚未全部合并前，必须保持能力状态为 `Designing`。

## 2. 角色与必备证据

维护窗口开始前必须指定发布负责人、数据库负责人、应用负责人和回退决策人，并准备以下可定位证据：

- 目标提交、应用版本、数据库实例和当前 DbUp Journal 版本；
- `UuidStorageContractV1` 合同检查通过记录；
- 生产等价备份及独立环境恢复成功记录；
- 008/009 空库、存量升级、半完成恢复和冲突拒绝测试记录；
- API、Worker、Migrator 使用同一 Binary16 连接策略的构建产物；
- SQL Server 聚集索引基准与 MySQL 行数、唯一性、引用和摘要基线；
- 已批准的破坏性 DDL 豁免标识、维护窗口起止时间和业务通知。

证据不得包含连接串、Secret、Token 或业务数据样本。

## 3. Go/No-Go 门禁

只有以下条件全部为“是”才允许开始：

1. 迁移编号已冻结，007 为 Seed 审计，008/009 未被其他分支占用，命名迁移已顺延为 010/011；
2. 当前数据库只包含已批准的 001–007 或已验证的 008 Expand 状态；
3. 备份已完成，且恢复演练证明可在目标 RTO/RPO 内恢复；
4. API、Worker、定时任务、导入器和第三方直写工具均能在窗口内停止；
5. 当前事务可排空，Outbox lease 的最长到期时间和 Seed 锁超时已知；
6. 23 个登记 UUID 列的行数、非空数、Distinct 数、引用缺失数和摘要已记录；
7. Binary16 应用镜像、旧应用镜像和数据库恢复介质均可用；
8. 双库冒烟脚本与回退负责人已就位。

任一条件为“否”或“未知”都必须 No-Go，不得靠临时关闭约束、跳过坏行或延后核对继续。

## 4. 维护窗口执行顺序

### 4.1 冻结与备份

1. 冻结迁移、发布和所有数据库结构变更；记录目标提交和 DbUp Journal。
2. 创建一致性备份，并在隔离环境恢复；验证关键表可读、行数一致且恢复日志无错误。
3. 保存合同中 23 个 UUID 列的基线计数与确定性摘要，只记录聚合结果。

### 4.2 停止写入并排空

1. 从流量入口摘除 API，停止 Worker、Migrator、导入器、计划任务和第三方直写工具。
2. 等待在途事务完成；等待 Outbox lease 与 Seed 数据库锁超过其最大有效期。
3. 通过数据库连接、锁和应用遥测确认没有写入者；仅停止进程但未核对数据库活动不算完成。

### 4.3 执行或核对 008 Expand

1. 如果 008 尚未执行，运行 Migrator 执行 008；如果已执行，先确认 DbUp 记账和真实影子对象一致。
2. 核对每个影子列、同步触发器、源/目标非空数、Distinct 数与 `BIN_TO_UUID(Binary, 0)` 往返。
3. 对 008 后产生的增量执行 delta backfill，再次核对行数、唯一性、引用关系和摘要。
4. 发现非法 UUID、源/目标冲突、空目标、孤立引用或缺失触发器时立即停止。

### 4.4 执行 009 Contract

1. 再次确认所有写入者停止、备份有效、维护窗口令牌和破坏性 DDL 豁免已登记。
2. 运行 Migrator 执行 009；不得手工拆分执行或跳过前置检查。
3. 验证 canonical UUID 列均为 `BINARY(16)`，可空性、主键、外键、唯一约束和查询索引均与合同一致。
4. 验证 legacy 列、同步触发器和过渡标志按 009 合同退出，DbUp Journal 已记账。

### 4.5 部署与冒烟

1. 部署统一配置为 `GuidFormat=Binary16` 的 API、Worker、Migrator 和导入适配器。
2. 在 SQL Server 和 MySQL 分别执行租户解析、登录/刷新、权限导航、Outbox、Seed Baseline/Development 和 QueryMultiple 冒烟。
3. 验证新写入 UUID 为 v7、主外键可连接、审计与 Outbox 引用完整，MySQL `BIN_TO_UUID(value, 0)` 与应用文本一致。
4. 先恢复后台处理并观察，再按小流量逐步开放 API；持续监控数据库错误、Outbox backlog、认证失败率和引用完整性。

## 5. 停止与回退边界

### 5.1 009 之前

008 只增加影子对象且旧列仍为 canonical。失败时必须停止写入，记录失败点；确认旧列未被修改后，可按版本化清理脚本删除 008 影子列和同步触发器，恢复旧应用。禁止在未核对源列完整性时直接清理。

### 5.2 009 开始之后

009 会切换 canonical 列、约束和连接模式。此后禁止只回滚应用或把连接串改回 Char36。任何无法在已测试的 009 恢复路径内继续的失败，都必须：

1. 保持流量和全部写入关闭；
2. 保存迁移日志、DbUp Journal 和聚合诊断，不继续手工修表；
3. 恢复维护窗口前已验证的数据库备份；
4. 部署与该备份匹配的旧应用；
5. 完成双库冒烟后再决定是否恢复流量。

009 后的回退必然包含数据库恢复，不能承诺仅靠应用版本回滚。未完成恢复演练时必须 No-Go。

## 6. 完成记录

窗口结束后记录：目标提交、数据库版本、开始/结束时间、停机时长、迁移耗时、23 列聚合核对结果、双库冒烟结果、RPO/RTO、异常与处置。只有发布计划要求的生产等价证据全部存在，能力矩阵才能按 `Designing` → `Implemented` → `Build-verified` → `Verified` 的门禁提升。
