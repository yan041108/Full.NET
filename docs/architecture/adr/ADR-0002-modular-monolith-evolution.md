# ADR-0002：强化型模块化单体与按证据拆分

- 状态：已批准
- 日期：2026-07-18
- 修订：2026-07-22，明确模块项目拓扑门禁；2026-07-26，增加表所有权与消费方 Port 门禁；2026-08-07，明确模块内/模块间数据关联与事务标准
- 决策者：项目所有者在当前任务中明确确认
- 适用范围：Full.NET 1.0 总体架构、宿主职责和后续模块运行拓扑演进
- 来源评估：[Full.NET 综合架构方案评估](../../verification/architecture-assessment-2026-07-18.md)
- 正式规格：[Full.NET 总体架构设计规格](../../superpowers/specs/2026-07-17-fullnet-architecture-design.md)

## 背景

Full.NET 当前定位是面向管理系统、企业应用和中小型 SaaS 的快速开发底座。代码已经具备显式模块入口、集中 Composition、API/Worker/Migrator Host Profile、双数据库迁移、事务 Outbox、缓存和架构测试；真正落地的业务模块当前主要是 Identity 与 Tenancy。

需要在快速交付、模块生态和未来独立伸缩之间建立稳定边界。过早全面微服务化会放大双数据库、协议版本、可靠消息、部署和测试成本；只保留松散单体约定又会让模块随着业务增长直接共享内部代码和数据表。

## 候选方案

### 方案一：强化型模块化单体

业务模块默认同进程运行，通过公开 Contracts 通信并拥有自己的表；API、Worker、Migrator 按运行角色分离。用架构测试、数据所有权和可靠消息门禁保持可拆分性。

### 方案二：按模块多宿主或分布式单体

提前把部分业务模块放入独立进程。它能够提供局部伸缩和故障隔离，但如果数据、事务和契约尚未自治，就会同时承担网络复杂度和内部耦合。

### 方案三：全面微服务

每个模块成为独立服务和数据所有者。它提供最大的部署自治，但当前模块数量、可靠消息成熟度、运维需求和团队边界不足以证明其成本合理。

## 决策

采用方案一，并保留按证据向方案二演进的通道：

1. Full.NET 1.0 采用强化型模块化单体，不进行全面微服务化。
2. 模块内部实现默认 `internal`，跨模块只依赖公开 Contracts；模块拥有自己的表，禁止直接访问其他模块内部表。
3. 每个内聚业务模块默认只有一个主项目，小功能作为项目内垂直切片；Contracts 和传输适配项目只能按真实消费者与隔离收益选择性增加，不能作为模板标配。
4. API、Worker、Migrator 按运行角色分离，AppHost 只负责编排。角色分离不等于业务服务拆分，也不自动要求每个模块拆出 `.Http` 或 `.Worker` 项目。
5. 同进程同步调用不序列化；可靠异步副作用通过事务 Outbox 和 Integration Event；gRPC 只在首次真实跨进程同步调用出现后引入。
6. 不为未来可能的扩容、团队增长或技术偏好预先引入服务发现、网关、服务网格或分布式事务。

## 模块项目拓扑门禁

模块项目采用“一个主项目＋按证据可选 Contracts/传输适配项目”：

1. CRUD、实体、菜单和用例只形成主项目内的目录与垂直切片，不得单独建立项目；
2. 独立 Contracts 项目必须存在真实跨模块或外部编译期消费者，并用于隔离稳定公开契约；
3. 独立 `.Http`、`.Worker` 或其他适配项目必须证明同一核心被非该传输宿主复用，并产生可验证的依赖、打包或安全收益；
4. 新增可选项目必须在已批准 Spec 或计划中记录消费者、依赖方向、收益和对应架构测试；
5. 缺少上述证据时保持一个主项目，通过 `internal`、命名空间、显式注册入口、Host Profile 和架构测试维持边界。

当前 `Identity.Contracts` 与 `Organization.Contracts` 已有真实跨模块消费者，可以保留；`Tenancy.Http` 是待结合依赖硬化结果复核的存量拆分，不构成新模块模板。是否合并存量项目必须单独评估引用图、宿主装配和回归成本，不在本次文档决策中静默执行。

## 数据所有权与消费方 Port 门禁

1. 生产模块中的显式 SQL 必须只访问本模块拥有的 `fn_<module>_*` 表；架构测试从源码提取表名并按模块目录校验所有权。
2. 当前确有迁移成本的跨模块只读查询只能在 [`module-table-access-debt.json`](../../../contracts/architecture/module-table-access-debt.json) 中按来源模块、表和文件精确登记；禁止通配符，登记项必须包含原因与移除里程碑，失效债务也会使门禁失败。
3. 模块 A 的用例需要模块 B 提供能力时，优先由消费方 A 在自身 Contracts 中定义最小 Port，由 B 实现适配；不得为了一个用例让 A 的实现项目反向依赖 B 的 Contracts。
4. 现有公共 Contracts 不因内部依赖调整而静默删除或改签名；迁移期可以让同一适配器同时实现旧契约与消费方 Port。

## 模块内/模块间数据关联与事务标准

Full.NET 以业务不变量而不是菜单、页面或物理表数量划分模块。共享数据库只降低当前部署成本，不扩大任一模块的数据所有权，也不构成跨模块关联或事务授权。

| 场景 | 默认实现 | 事务边界 | 禁止事项 |
| --- | --- | --- | --- |
| 模块内读取关联 | 对本模块表使用参数化 `JOIN/LEFT JOIN`、批量查询或多结果集 | Query 默认无显式事务；需要一致快照时由用例显式声明本模块只读事务和隔离要求 | 为复用而建立跨模块 Repository，或用逐行查询制造 N+1 |
| 模块间立即读取 | 消费方最小只读 Port/对方公开 Contract Service；列表必须提供批量投影 | 不宣称跨模块快照一致；远程化后由适配器增加 Deadline、取消、认证和追踪 | 直接读取、JOIN、视图封装或存储过程访问对方表 |
| 模块间高频读取 | 所有者发布版本化 Integration Event，消费方维护自己的本地投影 | 所有者数据与 Outbox 同事务；消费方独立幂等提交，属于最终一致 | 消费事件时逐条反查所有者、用旧版本覆盖新投影，或把缓存当权威状态 |
| 模块内写入 | 一个用例由一个 `ICommandTransaction` 原子维护本模块业务表、B0 Domain Audit 和必要 Outbox | 单连接、本地数据库事务；异常、取消和超时必须回滚 | 在事务内执行不可回滚 HTTP、gRPC、Broker、Redis 或文件副作用 |
| 模块间写入 | 将强不变量收敛到唯一所有者；其他模块通过 Outbox 事件和幂等消费者推进 | 每个模块只提交自己的本地事务；跨模块采用最终一致、补偿和对账 | 新流程依赖共享 `DbSession`、跨模块本地事务、分布式事务或跨模块写表 |

补充约束：

1. 只有同一模块拥有的表可以在生产 SQL 中直接关联；禁止通过数据库视图、同义词、存储过程、触发器或动态 SQL 隐藏跨模块读写。
2. 跨模块同步读取只适合请求当下必须获得权威答案、调用频率和故障耦合可接受的场景；高频列表、报表、搜索和可容忍传播延迟的决策优先使用本地投影。
3. 同步 Port 在模块化单体中使用同进程实现，不序列化；首次真实跨进程消费者出现后，由 Composition/传输适配层替换为 gRPC 或 HTTP Adapter，消费方用例不得感知传输实现。
4. Contract Service 的返回值可能在调用结束后立即变旧。若某项校验必须与写入保持强不变量，该校验和写入必须归属同一模块；不能用“先读模块 B、再写模块 A”冒充原子性。
5. 新业务流程不得依赖跨模块本地事务。确有迁移期存量依赖时，必须按调用方、所有者、入口、事务范围、风险和移除里程碑精确登记，且不得把该债务作为新实现模板。
6. 跨模块引用只保存对方稳定标识和本模块所需快照，不建立跨模块数据库外键；引用有效性由所有者 Contract、事件投影、状态机或对账流程维护。
7. 领域参数属于执行业务不变量的模块。预约、支付、工作流等参数必须使用强类型、作用域、版本和生效时间表达；通用 Settings 只能承载平台级通用设置和管理入口，不得成为任意业务参数字符串仓库。
8. 小型领域参数变更事件默认携带完整强类型快照与单调版本，消费者按稳定 `MessageId` 或业务键幂等处理，并拒绝旧版本覆盖新状态；管理 API 返回成功只表示权威源与 Outbox 已提交，不表示所有消费者已经收敛。

当前 `015_HostRoleDataScope` 中 `fn_identity_role_data_scope_unit.UnitId -> fn_organization_unit.Id` 是已识别的存量跨模块外键，不构成新代码先例。它必须在[模块数据访问与一致性边界硬化计划](../../superpowers/plans/2026-08-07-module-data-access-and-consistency-hardening.md)中登记、验证替代完整性机制并通过成对可恢复迁移移除；完成前能力状态不得表述为“跨模块外键债务已清零”。

## 局部服务拆分门禁

局部模块只有同时满足以下条件，才可以提交拆分 ADR 和后续实施计划：

1. 存在可测量的独立伸缩、SLA、故障隔离或发布节奏需求；
2. 模块能够独占写入自己的数据，不访问其他模块内部表；
3. 目标业务流程不依赖跨模块本地事务；
4. Integration Event 或 RPC 契约已经版本化并具有兼容测试；
5. Outbox、重试、死信、重放和可观测性已经在生产等价拓扑验证；
6. ADR 证明独立部署收益高于新增运维、测试和故障处理成本。

缺少任一条件时，优先在模块化单体内部解决边界、性能或可靠性问题，不得用独立进程掩盖耦合。

## 后果

正面后果：

- 保留同进程调用、事务、调试和部署的低成本；
- 模块边界能够先在代码、数据和契约层得到验证；
- API、Worker、Migrator 可以按资源模型独立扩展；
- 未来局部拆分有明确证据门槛，不依赖主观偏好。

成本与限制：

- 共享数据库实例需要持续执行表所有权和跨模块访问审查；
- Composition、公开类型和模块依赖图必须随着模块增长保持自动化门禁；
- 项目边界不再机械等同于功能边界，团队需要在新增可选项目时提供可审查证据；
- 热点模块在满足拆分门禁前仍受主应用发布节奏约束；
- 独立服务不是 1.0 默认交付能力，不能据此宣传微服务就绪。

## 与现有基线的关系

- 本 ADR 明确并收紧总体架构设计中“模块化单体优先、按需拆分”的既有方向，不推翻 Dapper-first、双数据库、Outbox 或多租户基线。
- 架构硬化设计中的可靠消息、缓存一致性、双数据库 SQL 和 Host Profile 继续有效，并构成服务拆分前置条件。
- 能力状态矩阵已经把模块化单体与 Host Profile 标记为 `Build-verified`，把 gRPC 标记为 `Planned`；本决策不提升任何实现状态。
- 后续若改变为全面微服务或放宽任一拆分门禁，必须新增替代 ADR 并同步总体规格。

## 验证

- 总体架构规格必须引用本 ADR，并保留相同的六项拆分门禁；
- 新模块规格与计划必须列出逻辑模块、主项目、可选项目及其门禁证据；没有证据时只能创建一个主项目；
- 每个跨模块用例必须声明数据所有者、读取模式、事务所有者、一致性等级、失败恢复和未来远程适配边界；
- 架构门禁必须拒绝跨模块表访问、隐藏式数据库关联和未登记的跨模块本地事务债务；
- 运行与部署章节必须保持 API、Worker、Migrator 职责分离；
- 能力状态矩阵不得因本 ADR 把未实现的 gRPC 或独立服务标记为已实现；
- 链接、占位符和 `git diff --check` 必须通过。
