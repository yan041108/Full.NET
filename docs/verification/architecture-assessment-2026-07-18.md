## 1. 评估目标

本次评估在以下目标之间取得平衡：

1. 保持项目快速交付和较低运维成本；
2. 支持 Full.NET 长期扩展为模块生态；
3. 为大规模 SaaS 的独立伸缩和故障隔离留下演进通道；
4. 不为尚未出现的规模、团队和部署需求提前承担分布式复杂度。

当前 Full.NET 不是从零选型。仓库已经形成模块化单体骨架、显式 Host Profile、API/Worker/Migrator 角色分离、双数据库迁移、事务 Outbox、多租户安全边界和架构测试。本次比较重点是是否继续强化现有基线，以及何时允许局部拆分。

## 2. 方案比较

| 方案 | 交付效率 | 扩展能力 | 运维成本 | 一致性复杂度 | 当前适配度 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 强化型模块化单体 | 高 | 高 | 低 | 低 | 最佳 |
| 按模块多宿主或分布式单体 | 中 | 较高 | 中高 | 中高 | 未来局部采用 |
| 全面微服务 | 低 | 很高 | 很高 | 很高 | 当前不适合 |

### 2.1 强化型模块化单体

继续以同进程业务模块为主，模块保持单程序集和垂直切片；内部实现默认 `internal`，只通过 Contracts、Command/Query 和 Integration Event 暴露边界。API、Worker 与 Migrator 按运行角色分进程，但不把这种角色分离误称为微服务。

主要收益：

- 同进程事务、调用、调试和部署简单；
- 适合继续交付 Organization、Settings、Files 等业务切片；
- Dapper 和显式 SQL 暂不承担跨服务查询与数据复制复杂度；
- SQL Server/MySQL 双提供程序验证可以集中实施；
- 可以通过架构测试、表所有权和模块依赖图控制边界退化。

主要风险是模块直接读取其他模块表、Contracts 膨胀、BuildingBlocks 业务化和 Composition 注册漂移。这些问题应先通过自动化边界治理解决，不需要用微服务作为第一手段。

### 2.2 按模块多宿主

将 Notifications、Jobs、Files 等具有独立资源模型的模块部署为单独宿主，核心 Identity、Tenancy 和 Organization 仍保留在主应用中。

该方案只有在模块已经具备稳定协议、独占数据写入、独立伸缩或故障隔离需求，并且不再依赖跨模块本地事务时才有收益。如果独立宿主仍直接访问其他模块的内部表，就会形成分布式单体：同时承担网络和部署复杂度，却没有获得自治能力。

### 2.3 全面微服务

每个业务模块成为独立服务、独立数据所有者和独立部署单元。当前不推荐采用，原因包括：

- 真正落地的业务模块当前主要是 Identity 和 Tenancy；
- Outbox 尚缺死信、跨版本升级和版本退役闭环；
- gRPC 服务通信仍为规划能力；
- Seed、破坏性迁移门禁和真实浏览器链路仍有待闭环；
- 双数据库已经显著增加测试矩阵，全面微服务会进一步乘法放大；
- Full.NET 的当前定位是快速开发底座，而不是已有稳定服务边界的大规模产品。

## 3. 当前架构判断

### 3.1 已形成的有效边界

- `Full.NET.Composition` 集中维护官方模块和宿主 Profile，避免各 Host 复制模块清单；
- `IFullNetModule` 保持精简，没有为假想初始化需求保留悬空生命周期；
- 模块实现大量使用 `internal`，Tenancy 的公共出口主要限制在 `Contracts`；
- Architecture Tests 已检查 BuildingBlocks 反向依赖、模块公开面、宿主 Profile 和 Dapper 边界；
- API、Worker、Migrator 已按运行角色分离，为后续按证据拆分保留了组合根。

### 3.2 需要优先加固的边界

1. **数据所有权**：共享数据库不等于共享数据模型。模块不得直接读取或写入其他模块表；跨模块读取应使用公开查询契约、投影或由事件维护的本地读模型。
2. **模块契约**：当前不为每个模块机械新增 Contracts 项目。首个真实跨进程消费者出现后，再评估提取独立程序集或 Protobuf 契约。
3. **可靠消息**：任何服务拆分前必须补齐最大重试、死信、版本升级、蓝绿兼容、退役和审计重放。
4. **组合根扩展**：当前显式分支对两个模块足够清晰。模块增长后应演进为静态模块描述符目录，禁止用大范围反射扫描或恢复 Host 手写清单。
5. **BuildingBlocks 控制**：只有至少两个真实模块需要、语义稳定且不包含业务规则的能力才能进入 BuildingBlocks。
6. **交付真实性**：近期优先完成生产 Seed、SQL 迁移安全、租户 SQL 语义守卫和真实后端浏览器 E2E，而不是服务拆分。

## 4. 推荐目标架构

```text
模块化单体
├── API Host：完整 HTTP 模块
├── Worker Host：最小事件消费者集合
├── Migrator Host：迁移与安全 Seed
├── 每模块单程序集
│   ├── Contracts：唯一公共边界
│   ├── Features：垂直切片
│   ├── Domain：内部领域规则
│   ├── Persistence：模块自有 SQL
│   └── Endpoints：模块 HTTP 适配
└── 共享数据库实例
    └── 表、迁移、查询和缓存均有明确模块所有权
```

目标是保留单体部署的低成本，同时建立接近独立服务级别的模块边界。模块边界先在代码、数据和契约层成立，部署拆分只改变运行拓扑，不用来补救内部耦合。

## 5. 服务拆分门禁

模块拆成独立服务前必须同时具备以下证据：

1. 存在可测量的独立伸缩、SLA、故障隔离或发布节奏需求；
2. 数据可以由该模块独占写入，不依赖其他模块内部表；
3. 业务流程不要求跨模块本地事务；
4. Integration Event 或 RPC 契约已经版本化并具备兼容测试；
5. Outbox、重试、死信、重放和可观测性已经过生产拓扑验证；
6. 独立部署收益经 ADR 证明高于新增运维、测试和故障处理成本。

通常更适合优先评估拆分的是 Notifications、Jobs、Files 和未来 AI/Agent 等资源模型独立的模块，而不是 Identity、Tenancy 等强一致性基础模块。

## 6. 建议实施顺序

1. **P0 生产可控性**：Seed Baseline/Overlay、破坏性 SQL 门禁、迁移恢复和真实状态治理；
2. **P1 可靠性**：Outbox 死信与版本闭环、租户 SQL 语义元数据、缓存一致性和高优先级日志通道；
3. **P1 交付真实性**：Vue/Layui 真实后端浏览器安全链路与跨 Tab 会话竞争；
4. **P1 模块扩展验证**：用 Organization 或首个完整后台 CRUD 切片验证模块、双库和双管理端交付边界；
5. **按证据演进**：只有命中第 5 节门禁后才为具体模块编写 ADR 和拆分计划。

## 7. 结论与未验证项

建议 Full.NET 1.0 继续采用强化型模块化单体，不改成 Clean Architecture 多项目矩阵，也不全面微服务化。长期演进原则是：保持单体部署成本，以自动化建立模块边界；证据出现时，只拆需要拆的模块。

本次为代码与文档静态评估，没有修改或运行产品代码，没有执行 Release 构建、单元测试、集成测试或性能基准。因此本文不提供吞吐量、容量上限、故障恢复时间或独立部署收益的实测证明。当前能力的权威状态继续以[能力状态矩阵](../roadmap/capability-status.md)为准。

## 8. 正式采纳记录

项目所有者于 2026-07-18 明确采纳以下长期架构决策：

1. Full.NET 1.0 继续采用强化型模块化单体；
2. API、Worker、Migrator 保持按运行角色分离，AppHost 只负责编排；
3. Full.NET 1.0 不进行全面微服务化，也不为未来假设提前引入网络边界；
4. 只有同时满足第 5 节服务拆分门禁并通过独立 ADR，才允许局部模块拆分。

该采纳只确认架构形态和演进门禁，不把第 3.2 节列出的加固缺口标记为已实现，也不授权本次任务修改产品代码或生成实施计划。
