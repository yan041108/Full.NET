# Logstash Kafka/PQ 单事件重启验证（2026-09-30）

- 范围：基线提交 `c609759576c4bf54ff9e743161ecb829ca8d4d4a` 加当前工作区候选；Windows Docker Desktop。本记录是独立平台消费者的局部实验，不是生产部署配置或准入证明。
- 固定镜像：`apache/kafka:4.1.2@sha256:5cc2a2fd93fa2687b44015eee04fb2c3edd9e526bd64bf8bec5ff1e268772e0e`；`docker.elastic.co/logstash/logstash:9.5.4@sha256:75a495fa0ce94f44da25b7458bf6bf68bb3e4ecde8cdd00cc4376d78fa64e1e7`。镜像内 `logstash-integration-kafka 12.1.9`、`logstash-output-elasticsearch 12.1.6`。镜像仅供本地测试；尚未评估生产再分发许可与目标平台供应链。
- 方法：单分区测试 Topic、测试专用 Consumer Group，Kafka 输入设 `enable_auto_commit=false`，Logstash 使用独立 Docker 卷上的 `queue.type=persisted`、`queue.checkpoint.writes=1`。先把 Elasticsearch 输出指向不可达地址；送入一个固定 `LogEventId`，待 PQ API 报 `events_count=1` 且 Broker Group 的 `CURRENT-OFFSET=1`。对 Logstash 发送 SIGKILL，保留 PQ 卷，**停止 Broker 后**改为 stdout 输出重启同一输入与队列；待原 ID 输出且 PQ 清空，再启动 Broker 核对 Offset。
- 结果：初始手工过程和恢复阶段 Broker 在线的脚本各通过一次；独立审查指出在线 Broker 不能排除重新消费，最终结果以 Broker 离线的复测为准。离线恢复时原 ID 输出一次、PQ `events_count=0`，Broker 重启后 Group Offset 保持 1。`logstash -t` 对阻塞和恢复配置均返回 `Configuration OK`。
- 结论与限制：只观察到“PQ 中已有记录、Broker Offset 已提交”这一崩溃窗口，**不能证明每事件 checkpoint/fsync 一定早于 Offset 提交**。更关键的是，Elastic 官方明确说明 Kafka 输入可能在事件安全进入 PQ 前提交 Offset；因此现有 Logstash Kafka 输入/PQ 组合与本项目可靠档的持久先于提交要求冲突，不能靠该单事件恢复结果准入。尚未验证首个写入中途崩溃、分区乱序或重平衡、PQ 卷损坏/丢失、ES Bulk 逐项结果、DLQ 持久隔离、查询/归档、TLS/SASL 凭据、节点持久卷或持续吞吐。运行时 PQ API 报 `dead_letter_queue.storage_policy=drop_newer`，坏记录隔离不能因此认定可靠。生产 Kafka 消费组合和 Collector 门禁均保持关闭。
- 依据：[Logstash 官方 Kafka/PQ Offset 限制](https://www.elastic.co/docs/reference/logstash/tips-best-practices)、[Kafka 输入的 `enable_auto_commit` 配置说明](https://www.elastic.co/docs/reference/logstash/plugins/plugins-inputs-kafka)、[PQ 与 checkpoint 限制](https://www.elastic.co/docs/reference/logstash/persistent-queues)。输入插件文档所述“写入队列后提交”不等于安全落盘先于提交；本记录保留局部恢复事实，不作为可靠档准入证明。
